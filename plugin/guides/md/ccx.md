## Compact Context (ccx)

`cc-context` — the `ccx` CLI and the `cc-context` MCP (its tools mirror the query surface — read, search, symbol, outline, diff, edit — plus `ccx_exec`/`ccx_exec_tools` for multi-call composition and `BashFormat` for JSON re-encoding) — is the first stop for TARGETED code questions: a file section, a symbol, a search, a diff. It returns token-bounded output (signatures + line numbers, explicit overflow, never silent truncation) instead of raw dumps, and the capt-hook `ccx` guard pack rewrites the mappable token-heavy commands (raw `grep`, bare `git diff`/`git show`, page-dump `curl`, oversized `Read`s) to their ccx equivalents in place and BLOCKS the rest. That budget discipline covers ccx itself: never re-truncate ccx output with `| head`/`| tail` — it re-introduces silent truncation and eats the overflow footer; raise `--budget`, narrow with `--section`/`-g`, or compose with `ccx exec` (entry 16).

1. **Orient a repo** → `ccx repo overview`
2. **"How does X work / where is Y" (intent)** → `ccx code search "<question>"` (semantic — a native in-process engine, no external process; model weights download once into a local cache on first use; `--content` narrows the corpus, space-separated `code|docs|config|all` defaulting to `code docs`, honored by `ccx code search`/`related` and the MCP search/related tools)
3. **A specific symbol (where + signature)** → `ccx code symbol <name>` (alias `ccx code grok`; terse by default with a counts trailer — `--callers`/`--callees`/`--body`/`--full` expand, `--budget N` caps an expanded card)
4. **Literal or regex text** → `ccx code grep <text> [paths...] [--regex] [-g GLOB]... [-i] [-w]` (literal-first with auto-regex: a zero-match literal pass whose pattern carries regex metachars and compiles reruns as a regex, the header saying `(auto-regex)` — so `a|b` works without the flag; `--regex` forces regex from the start; `--regex`/`-i`/`-w` and explicit file operands run on ripgrep; system `grep` fills in when `rg` is missing. `-g/--glob` is the one file selector — repeatable and ordered in ripgrep's gitignore dialect: `!` excludes, last match wins, any include turns the set into a whitelist, a slash-less pattern matches basenames at any depth, and it filters within explicit paths too; shared by `code symbol`, `vcs diff`, and `vcs show` (on those two a slashed glob is repo-root-relative rather than cwd-relative, since they filter git's changed-file list instead of walking the tree), while `--scope` is deleted everywhere (unknown flag, not a deprecation). One ccx twist raw ripgrep lacks: a metachar-free glob naming a real directory means its subtree — `-g internal` searches `internal/**`, the drop-in for the old `--scope D` (`--scope D --glob G` → `-g 'D/**/G'`). A glob anchored at a real path — `-g '.venv/**/*.py'` — is searched even where ignore rules would hide it, but only while every include shares that anchor: add `-g '*.sh'` and the ignored tree silently drops out — put both under the anchor (`-g '.venv/**/*.{py,sh}'`) or make two calls)
5. **List files** → `ccx repo find <glob...> [--budget N]` (globs are positionals — repeatable, ordered, same gitignore dialect and bare-directory rule as entry 4's `-g`, so `ccx repo find internal` lists `internal/**`; gitignore-honoring, VCS stores skipped, sorted; budget-capped with a footer counting withheld rows and ignore-hidden files; a glob anchored at a real path — `.venv/**/*.py` — lists files ignore rules would hide; orientation is entry 1, not `"**/*"`)
6. **Read a file** → `ccx code outline <file-or-dir>` first (ast-grep structural map for the languages it outlines and any directory, a markdown heading outline or an honest head window otherwise; top-level by default — `--deep` expands members, `--section A-B` windows a file), then `ccx code read <file> --section A-B` for the part you need (whole file: `ccx code read <file> --full`)
7. **Edit a file** → `ccx code edit <file> --at A-B#hash --content <text>` (hash-verified write: refuses on anchor mismatch, re-anchors moved content, returns the new anchor so edits chain; `--content -` reads stdin, `--delete` removes the range; `--match <text>` addresses by exact bytes instead of a span — an ambiguous match errors listing candidate anchors, `--at` scopes the scan, `--all` replaces every occurrence)
8. **Review changes** → `ccx vcs diff [src]` (structural, jj-aware; exact hunks: `git diff -- <file>`)
9. **Inspect one commit** → `ccx vcs show [ref]` (message + structural per-file diff; default `@-`/HEAD)
10. **How a file evolved** → `ccx vcs history <path> [-n N]` (per-commit sha · date · subject + changed symbols)
11. **Locate a repo/module/package on disk** → `ccx repo locate <name>` (sibling repo, Go module, or Python package by import or dist name; prints tab-separated `kind`/`path`/`version` rows — an installed Python package yields both its sibling `repo` row and its installed `package` row; exit 3 when nothing resolves)
12. **Read installed dependency source** (`.venv`, site-packages, vendored) → spawn the `cc-context:dep-reader` agent with the package and your question — cited conclusions come back, the source never enters your context. Inline: `ccx repo locate <pkg>` for the on-disk path, then entries 4/6 with that path (`-g <path>` or an anchored glob) — never raw `rg` into `.venv`
13. **Commit, push, watch CI** → `ccx vcs ship -m "<msg>" [paths...]` (jj-aware commit + push + a watch over every workflow run on the pushed commit, in one call — per-run `workflow · conclusion · duration · url` report, plus failing jobs and a `--budget`-capped log excerpt when a run goes red; trailing paths scope the commit to just those files, leaving the rest of a shared working copy untouched; scoping goes below the file too — `ccx vcs hunks [paths...]` lists every pending hunk as a stable `file:A-B#hash` ref, and repeatable `--skip-hunk <ref>`/`--only-hunk <ref>` commit a file partially without ever rewriting it on disk, leaving excluded hunks (a concurrent session's, say) uncommitted in `@`, and refusing outright when a selection would cut an empty commit or a ref has drifted; an empty working copy refuses outright too (`nothing to commit` — a prior ship likely already landed it) instead of cutting an empty duplicate; and where the commit goes is one decision, resolved before any mutation and reported as a `branch <name>` or `created <name>` segment — on a non-trunk branch or bookmark ship appends to it, on trunk it appends in your own repositories and starts a branch when GitHub positively says the repository is someone else's (an org trunk rejects the commit through its protect hook and leaves it dangling; the gt lane always branches on trunk, since gt has no verb that commits onto it; ccx derives the name from the commit subject itself, slugified and capped, keeping the `Claude-Session-Id` trailer out of it), a detached HEAD or an ambiguous trunk refuses, and `--branch <name>`, `--new-branch[=<name>]`, `--append`, and `--allow-trunk` state intent explicitly (`--bookmark` is the jj-only alias of `--branch`, `--create` the deprecated alias of `--new-branch`; an explicit new-branch name is spelled `--new-branch=name`, since a bare `--new-branch name` parses `name` as a path); an updated remote is handled in-call on both backends — ship fetches first and rebases the stack onto the target (jj bookmark, or `origin/<branch>` on plain git, autostashing uncommitted work), rolling back and reporting a rebase that would conflict, and a push that still loses the race to a concurrent push re-fetches, re-rebases, and retries up to 3 attempts before failing with the manual recovery steps — though a rejected `--amend` push refuses instead of force-retrying over the other session's work). A live Graphite config (`.git/.graphite_repo_config`, resolved through the git common dir so a linked worktree counts) makes the gt lane a candidate — even in colocated jj repos; `--no-gt` falls back to the jj>git detection, and three gates run before any mutation, each demoting to the jj/git lane with the reason named in a leading `lane <kind> (<reason>)` segment: `ccx.nogt` set in git config (the durable opt-out for a repo carrying a stale Graphite config), GitHub positively saying the repo is someone else's — public, and you neither administer it nor share an owner or organization with it (a lookup that cannot be made keeps the lane) — and a cached probe of whether Graphite can actually submit here, since the config alone only proves `gt init` once ran (a probe that times out or cannot reach Graphite demotes too — a lane nobody could confirm is not one to ride — and each verdict caches for its own span: a yes a day, a no an hour, an unanswered probe a minute, so an outage costs one probe a minute, not one per command). On the gt lane commits go through gt (`gt create <name>` starts a stacked branch, `gt modify -c` appends to one, `--amend` amends the branch tip; an untracked branch is adopted first with `gt track -f`, `--parent` naming its parent), and the push becomes `gt submit` of the downstack — published by default, `--draft` opts out, `--publish` says so explicitly — with no fetch/rebase/retry, since gt owns restacking: ship refuses up front on a `needs_restack` anywhere on the downstack (`gt restack`, then re-run), on a branch gt cannot adopt, or on `--amend` on trunk, and a failed submit reports gt's recovery step (`gt restack`/`gt sync`/`gt auth`) instead of retrying, the report reading `submitted <branch> → PR #<n> <url>`. Ship owns the pull request in every lane: `--pr-title`/`--pr-body-file` are repeatable and branch-scoped (`<branch>=<value>`, a bare value applying to the tip; `--pr-body-file -` reads stdin once, and every body file is read before the commit forms) — outside the gt lane ship opens the branch's PR when there is none and edits exactly the fields this invocation restated when there is, so a hand-edited description survives a re-ship that does not mention it; in the gt lane it fills the title and body `gt submit` leaves empty, the only way a downstack PR gets a body at all; `--draft`/`--publish` apply in every lane, converting an existing PR in either direction, `--no-pr` opts out, and a ship naming no PR flag makes no `gh pr` call. `--reviews` chains a review watch (entry 14) after the CI watch. A red run hands off to the `cc-context:ci-triage` agent — spawn it with the run id for root cause, a minimal excerpt, and the next step instead of the full log
14. **Stream PR review comments** → `ccx vcs reviews [pr-or-branch...]` (attaches to open PRs — positionals mix PR numbers and branch names, none → the current branch's PR, `--stack` → the Graphite downstack — and polls every `--interval` (default 30s), streaming each review verdict, inline comment, and issue comment as one block with author, locus, and a `--budget`-capped body; a `changes_requested` review carries a pointer to spawn the `cc-context:pr-review-triage` agent with the PR and review id; the watch exits when every watched PR is merged or closed, and Ctrl-C prints the exact resume command; `--since` replays history — RFC3339, a duration ago like `90m`, or `all`, default now — so arm a `Monitor` on `ccx vcs reviews --since 5m` right after a ship to close the gap between push and attach; the watch is at-least-once, so a resume may re-print events already seen; `ship --reviews` chains the same watch in-call after CI)
15. **Bring the stack current with trunk** → `ccx vcs stack restack` (alias `rebase`; lane-selected like ship, gates included — the gt lane runs `gt sync`, jj fetches and rebases the working-copy stack onto `trunk()`, plain git fetches and rebases onto the remote default branch with `--autostash`; a conflict always refuses with the lane's recovery steps — `gt continue`/`gt abort`, a rolled-back jj rebase, an aborted git rebase — never headless resolution; `--no-gt` forces the jj/git lane). A stack holding one branch per working copy restacks in place: git will not move a branch a sibling checkout has checked out, so gt is driven once from each holding working copy, bottom-up. The rest of the group cuts and lands such a stack — `ccx vcs stack new <name>` cuts a branch stacked on this one **in a working copy of its own**, leaving the calling one on its branch, `ccx vcs stack list` names the working copy holding each branch, and `ccx vcs stack submit` restacks every lane and then submits the whole stack
16. **Compose several calls / post-process any output** → `ccx exec '<python>'` — a sandboxed script whose async host functions are every ccx query op, a gated `sh(cmd)`, and every stateless MCP server's tools (auto-reflected, no flag needed); only the script's return value enters context. Rule of thumb: one question → one ccx call (entries 1–15, 17–22); a pipeline, filter, fan-out, or any output you'd immediately post-process (project a JSON blob, sweep signatures across files, join search hits) → exec. Discover the host functions and the Python-subset rules with `ccx exec --list-tools` (MCP: `ccx_exec_tools`), once per session.
17. **Re-encode JSON tool output** → `ccx format -- <cmd>` (or `… | ccx format`) — a shape classifier picks the leanest encoding (prose, markdown table, CSV/TSV, TOON, TRON, JSONL, or compact JSON), never larger than compact JSON by bytes; `--format=X` forces one encoder
18. **Map a web page** → `ccx web outline <url>` (heading tree with stable `§` section refs; pages cache 24h, `--refresh` refetches)
19. **Read one section of a page** → `ccx web read <url> --section <ref>` (budget-capped section subtree + prev/next nav; whole page: `--full`)
20. **Ask a question of a page** → `ccx web search <url> "<question>"` (top-k relevant chunks with `<url> §2.3#hash` cites; hybrid BM25 + local embeddings — native in-process, no `uv`; BM25-only with a note when the model weights are unavailable, i.e. offline with an empty cache)
21. **Which lane a mutating vcs command takes, and why** → `ccx vcs info` (alias `lane`; vcs kind, repo root, branch, trunk, dirty state, Graphite config/CLI/reachability, the GitHub repo record, and on the gt lane the downstack with each branch's PR and whether that PR has a body; `--json`, `--refresh` refetches the cached GitHub metadata and reachability verdict, `--no-gt`; fails soft when GitHub is unreachable)
22. **A repo's stated contribution rules** → `ccx vcs guidelines` (alias `contributing`; every PR template variant, `CONTRIBUTING.md`, code of conduct, and issue config, each served verbatim, never summarized — so a PR template can be reproduced down to its checkboxes; the GitHub payload caches for a day but local files re-read every run, since a branch switch changes `CONTRIBUTING.md` on disk; `--json`, `--refresh`, `--full` adds issue-template bodies, `--budget` caps per document)

Entries 9–15 and 21–22 are CLI-only (entry 12's `locate` step included) — the MCP mirrors the query surface (1–8) plus exec (16), format (17, as `BashFormat`), and web (18–20, as `ccx_web_outline`/`ccx_web_read`/`ccx_web_search`), not these.

A path operand missing its extension resolves itself across the path-taking ops: `pkg/events` where only `pkg/events.py` exists runs against the sibling and notes the substitution (`# note: pkg/events → pkg/events.py`); several candidates error listing them, none errors clean (exit 3) — never raw engine stderr.

A one-shot question about a page → spawn the `cc-context:web-fetch` agent with the URL and your prompt verbatim (the WebFetch drop-in: cited answer out, the page never enters your context); research spanning several pages → `cc-context:web-researcher`.

Durable prose — plans, reviews, memory files — cites code as `path:line#hash` (e.g. `internal/render/finalize.go:31#k2fa`); any later session resolves the cite statelessly with ccx, because the hash re-anchors by content even after the file drifts.

Reach for your **LSP** when the answer must be exhaustive/structural (findReferences, rename, goToImplementation) — and verify any complete-set answer ("every subclass", "every importer") by reading the candidate files: bounded views optimize for precision, not exhaustiveness — or spawn the `cc-context:enumerator` agent, which packages that gather-and-verify loop and returns the verified set with cites and named blind spots. Use **Grep/Glob** or `rg` only for literal content in non-source files (logs, JSON, YAML) — on source, raw `rg` is gated the same as raw `grep`.
