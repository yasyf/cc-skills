# Rules for every message to the owner

Every rule below is checked by `lr say` or a hook before anything posts. The [owner-message skill](../SKILL.md) holds the templates; this page holds the full rule text, moved here whole from the communicator brief so it lives in one place.

## Sending

Every message for him goes out through one call, the `say` tool on the plugin's `lr` MCP server (`lr say serve`). A running server moves itself to the installed lr at the next frame it receives once nothing is in flight, on the same stdio, so a fix to this tool reaches a live session with no restart.

It takes a one-line `title`, the reply as markdown in `md`, and, when the content has them, `picks`, each `Keep it :: what picking it does`, with one `recommended`, `links`, `prs`, `artifacts`, a `status`, and up to 8 live cc-present `blocks`, such as a table he can filter and open. The tool decides from that content where the reply lands; the communicator never picks surfaces.

Pass what he would otherwise follow in a line of text in `artifacts`, each `{title, kind, file}`, with `file` an absolute path. The kind picks what he gets:

| Kind | Takes | He sees |
|---|---|---|
| `code` | any text file, a log included | its bytes in a window on Chat, and a link in Slack that opens on his tailnet only |
| `transcript` | `cc-transcript show --json` output | its turns, the same way as code |
| `image` | a PNG, JPEG, GIF or WebP file | the picture itself in the Slack post, uploaded as a file on the status card or in his thread, never a title alone |

Every file is copied under the drive's state dir and stays on this Mac until an edit of the reply leaves it off. A file that does not read as its kind is left off with a warning. A pick card cannot carry an image file, so send an image in its own reply with no picks. A reply whose words say it has a screenshot, image or picture is refused with `NO PICTURE` unless an image artifact or a diagram goes with that post; take the words out or attach the image.

The tool's description owns the checklist a caller reads before sending. A missed item does this:

| Missed | What the hook or tool does |
|---|---|
| A reply asking him to tap, approve or answer, with no picks and no open PR he can approve | `lr say` attaches each open card or waiting PR the `md` names and nothing else. A reply that names none of them is refused, `NAME THE WAIT`, listing what waits, and one saying something waits when nothing does is refused, `NOTHING WAITS`. `tap_asks_carry_the_button` refuses the same ask on a cc-slack post to his DM that has no `--tap-pr` and is not a waiting card |
| A PR in `prs` that is merged or closed, another person's, outside the drive's PR ledger, or unread from GitHub | Refused with `NO APPROVE` naming each PR and why, and nothing posts. A PR whose row waits only on a read of its newest head is no refusal: `lr say` reads every such PR in one GitHub query, as `lr board read` does, and refuses only when that read does not land. Name such a PR in `md` as a plain link; a drive PR with no row gets its row from its lane's `opened` record first. Another person's PR stays off his list (his Nov 3 ruling), so it is never put to him for a tap |
| A PR the reply's own words call closed, withdrawn or not landing | Never joins `prs` from `md`, so it shows as a plain link with no Approve, whatever its ledger row still says. Listed in `prs` it is refused with `NO APPROVE`; reword the sentence if it does land. An edit that leaves a PR off `prs` takes its Approve off the message |
| A `message` that `cc-slack check-post` flags or could not check, one no pick sends, or one addressed to a name instead of a Slack id | Refused with `DRAFT FAILS CHECK-POST` and each finding, or `DRAFT UNCHECKED`, and nothing posts. Write it to the cc-slack post rules, with the person as a `<@U…>` mention, short paragraphs, settings as a list and identifiers in backticks, and send again. The card shows the text exactly as it goes out |
| Any other line with card, your yes, no, pick or word, and no card | Refused, quoting the line; pass the picks or the PR in `prs` and send again |
| A release word with no Platy card | Warns and posts; a lane's name or `the release lane` is no release word |
| An abstract change or an unanswered first question | Refuses, naming the sentence and the question; answer it in the text and send again, and a sentence opening `Unproven:` counts as answered |
| A bare cci record number in `md` | Moved to a hidden cite, and the result says so |
| Any other bare id, or a bare `Sentry <n>` | Refused, listing each one; make each a link and send again |
| A notebook link with no title | Warns and posts |
| An open PR a reply with no picks names, in `prs` or md, in CI or not | Joins `prs` by itself and draws his Approve at once; his tap is stored at that head, and landing still waits for green checks, the approving review and grades. A PR landed, closed, held or already tapped shows as a link, and one with no ledger row warns |
| An open bug named, its fix PR not in `prs` | Adds the fix PR to `prs` by itself; warns and posts where it cannot, as under Card shape |
| `by` or `routed` off a progress or info reply to an order with no picks | Left off with a warning |
| A PNG on `display.artifact` | The Talk surface fails and the result names it; live-primitives owns the artifact design |

| The reply carries | Where it lands |
|---|---|
| `diagram` | drawn on his Chat page by itself, as one architecture doc (arch/v1); the board, this window and Slack carry a link to its https dashboard page, and every pick card, Slack status card and reply in his Slack thread shows the diagram as a picture in that same post, drawn in Chrome from the dashboard; a store or log node's `medium` is one of memory, disk, bucket, keys or pages; a diagram or picture that does not draw refuses the reply before anything posts |
| anything | this window, as the markdown the tool returns; a cci record from `owner-relay` to `owner` on topic `reply:<id>`; the dashboard's store, `<state dir>/replies/<id>.json`; one card on this drive's Talk thread, beneath his latest note, carrying its `blocks` |
| `picks` | also one card on his board, which cc-present posts to his Slack direct messages with a button per pick, the recommended one first, and for each of `prs` its PR ledger row |
| his Slack message in a thread waits on a reply, with or without `picks`, a `progress` status included | also a text reply in that thread, the whole reply with its title on top, each PR and link as a line, and with `picks` a working copy of the card; `owner_returns` fills in `thread` from the row the reply's `order` or `on` names, and the communicator names `thread` only to answer a thread whose row the reply does not name |
| no `picks`, but `links`, `prs` or a `status`, and no `thread` | also one card at the root of his Slack direct messages, with each https link as a button, each http link, such as a tailnet one-pager, as a line of the card, and each PR as a link in its text, under which cc-slack posts the PR's card with Approve and Hold when it waits on his tap |

Card shape:
- Every card he reads, from any lane and any tool (`lr say`, a status card, a merge or tap card, a Slack line), meets one bar. It asks one question in one sentence, says what the choice is, whether he has to make it at all, and what it changes for a user, and each option says what picking it does in two sentences at most. Its body asks no second question, never opens by repeating the question and never says a paragraph twice. Counts go in a short table or a line of their own, never three to a line of prose. Its prose carries no record id, plan step, lane or incident name, commit hash, test corpus row such as C211, build or job name, test function name, or code term such as a type, field, route or code span; a test is named by what it checks, and an internal term by what it does, in one plain sentence. `lr say` and `lr say`, card files included, refuse a card that breaks it and name the word, so its lane rewrites it before it posts and no lane routes it by hand. The tap-card drawer holds a card that breaks it and tells the PR's lane to fix the title or body. The merge and tap cards replace each corpus row in a PR title with the description in that test's name at the PR's head. A PR card's ELI5 line is the reviewer bot's ELI5, its one- or two-line plain explainer of the change, read from GitHub in one call for every PR on the card; until the bot posts one it is the PR body's Context section.
- Any line saying something waits on him, a reminder or list included, from any lane on any surface, is itself the cards: pass each in `picks` or `prs`, so it re-posts with its buttons in that thread. A lane's `dm-status` carries it as `options` on its `--card`, or `--tap-pr` for a PR. A link to a card is only for a post that cannot carry one; a card you removed, or one gone stale, is said so in the same breath with its replacement; and with no card, write no "waits on you". A card the `md` names in passing, by its id, by `card <words>` or `<words> card`, or by its title, becomes a markdown link to the Slack message he taps it on; an id reads as the card's title.
- Every Slack card renders in Block Kit from `md` as markdown, with its bold, links, lists and table, split under Slack's limits and never cut. What passes a message stays behind Explain more.
- A card that names a PR says in its title what kind of change it is, port, fix, new or cleanup, and for a pick what he is choosing (owner m1887, m1888). A port says it is a port, and when it asks him anything, the line under its title says what differs in the new tree that forces the choice. `lr say` pick cards and every card a lane draws through the board link refuse a card that misses this, reading from the PR ledger whether a named PR is a port, and `lr card check` refuses a port PR whose Summary's first line does not say so.
- A pick or design card, a question with options, is sent by the lane that owns the question, with `lr say`, in plain words that meet every rule here (owner m2038, 9:04 PM Nov 8: "the lane itself that wants to send the message invokes that skill"). No lane hands its question to a drawing lane, to owner-relay or to root to draw.
- Every post to him that names a monorepo PR links it, whoever posts it, and the link shows where the PR stands, as below. A tap card comes from a reply's `prs`, which `lr say` passes as `cc-slack dm-status --tap-pr`, one per PR and head. On a reply with no picks, every open PR it names joins `prs` by itself, whatever its checks, so he can approve it the moment he reads it; a reply with `picks` that names a PR he can approve without listing it warns, as does one naming a PR he already tapped. A reply with `picks` passes none itself: its pick card draws each of `prs` on it, and marks each one he can approve `tap` unless a pick lands it, so the card's Slack message passes it as `--tap-pr` and carries its Approve. So a clean port or anything else that needs no tap is named by link and never listed.
- A post that names an open bug carries the tap cards for its fix PRs, with nothing listed by hand. A fix PR's body names the bug as `item <n>`, the number its `incident` record stamps, and the PR ledger keeps that body. `lr say` adds to `prs` each open, untapped fix PR of a bug the reply names, by `item <n>` or in words a `names-bug` judge matches to the PR's title and Summary. Where it cannot draw the card, it warns and posts. That covers a fix PR not ready for his tap on a reply with no picks, a reply with an approving pick, since a second PR unties that pick, a reply already at its ten PRs, an unsure verdict, and a judge that did not answer.
- A pick that says land, merge, approve or ship shows the PR it lands. With no `prs`, `lr say` draws the one PR in the drive's ledger its words name, and with none or several it warns `APPROVES NOTHING`. `lr say` already draws each PR its words name that GitHub holds, never a number inside a hidden `<!-- cci #N -->` citation, so it and `lr board cards check` warn on a landing pick on a card that links no PR. `owner_posts_carry_cards.py` warns on a bare number in `say` and in any Slack post to his DM, since a number shows no card unless a drive's ledger holds it.
- A pick that merges or approves a design doc or retro, a `Forge-AI/design-docs` PR, links the rendered doc: its GitHub Pages page, `https://docs.poetic.design/design-docs/<slug>/` or `/incident-retros/<slug>/`, its PR preview, `https://docs.poetic.design/previews/pr-<n>/<group>/<slug>/`, or a local render's tailnet link such as `lr explain` serves, never a link inside a hidden cite. Without one, `lr say`, the board's card check behind `lr say` and the `doc_merge_cards_link_the_page` hook on DM cards refuse with `NO DOC PAGE`.
- A card or pick that asks him to mint, rotate, revoke or renew a key, token, secret or credential, or to confirm a new one is in place, cites the `file:line` of the code that reads that credential. Without that line, `lr say` and the board's card check behind `lr say` refuse with `UNREAD CREDENTIAL`, and the ask goes back to its lane for diagnosis. On Nov 1 a card asked him to mint a tailnet key because of an error message. cc-remote enrolls through an OAuth client that never expires, so no key was owed.
- A PR card is one shape on every surface, drawn from the PR's row in the PR ledger (`lr board rows --json`) and the reviewer bot's ELI5 comment, nothing else: its link, title, where it stands in words, its ELI5 first, what it changes for a user, the plan row only when the PR departs from the plan, its show-me, what it waits on and its description. The show-me comes from the PR body's `## Show me` section and shows him the change the way that reads best: a fenced `arch` block (arch/v1) the card draws as its picture, a screenshot or gif when the change is visual, or a sentence (owner m1992 and m2007, Nov 8). A PR that adds a function also carries a real Sand API call and its result in a code block. `lr card check`, and `lr say` before his Approve, refuse a missing show-me, an arch block that does not draw, and a new function with no call. A card that names a mechanism, such as a skip, a fallback or a refusal, says on the card why it happens and what it costs him, so he never has to ask. Every card kind carries all four lines, a pick card, a status card's tap cards and a stack card alike. The plan row names the plan step the PR carries out; a grader's "checked against the plan" is not a plan row. cc-slack draws it in its own Block Kit blocks, above the card's buttons, with no badges and no Slack entity card. A tap on its link goes straight to GitHub. Each line is its own paragraph, so Slack folds a long one behind Show more and no text is cut; only what passes a message waits behind Explain more. A PR whose row lacks what it changes for a user, the plan row, an ELI5 or what it waits on refuses the whole post naming the PR and the missing line, and nothing goes out; its lane fixes the PR body, and `submit-pr` refuses a body without them, so a card never meets the gap. No reply passes its own lines.
- A Slack message a reply links, such as a card, a Platy release card or any other Slack post, reaches him as that message's card alone: Slack's unfurl, with no URL text in his sentence and no link line (owner m1809, Nov 6: "the link shouldn't be there at all just the card"). The `md` keeps the link for the board and the terminal. He taps on the card itself. `lr say` adds the link for each card name in the markdown, except a card his ccn answers already settle, which it leaves unlinked and names in a warning: take the words off the reply and run `lr board cards sweep`, which withdraws it when his answer was to that same question and otherwise tells the lane that drew it.
- A card lives in one place: at his DM root, or in the thread of the message he asked in, never both, and `lr say` posts no working copies. A second send for a live PR card or an open question edits that post in place; a send that would still post a second copy is refused and names the live post (owner m2010, m2040: "I only need one copy", "get rid of all the duplicates"). A card whose PR merges or closes is pulled by the supervisor at once, buttons gone and a Landed or Closed line in their place (owner m2020: "Next time do it before I tell you").
- A PR link in a post to his DM shows a preview cc-slack draws from the PR ledger: its title as a link to GitHub, all of what it changes, and where it stands, with a link to its card when it is ready for his tap. It reads `lr board rows` once per post through cc-slack's `preview_command`. A PR with no ledger row stays a link, and a line that only repeats a link is dropped, so name each PR once and never type its state beside it. Slack draws no preview of a private PR for a link an app posts, which is why this one is cc-slack's.
- Every release word to him says what users get, in plain words, and carries the Platy release card, which reaches him as its card alone, as the rule above says. The card is Platy's top-level #releases post for the build, the release lane's records carry its permalink in `--attr card`, and its What's new section supplies the plain words. A release number always has plain words beside it, and a PR-number list never stands in for them. `owner_posts_carry_cards.py` warns on a release word with no card link. See [release-lanes.md](release-lanes.md#start-a-release-and-post-it).
- `lr say` checks everything before anything posts. A rule it holds refuses, names the fix, and nothing goes out; a reply never posts with a warning (owner m2021). The one wait ahead of a post is the first-question judge and up to 30 seconds while his answers are judged against an open card the reply names.
- A notebook link is written as `[its title](url)`, since Slack draws no preview of one; a bare one draws a warning. A Buildkite build link shows its state and message in a preview cc-slack draws.
- A card opening on This, These, It or The change is refused. Name the thing and send again.
- `owner_cards_name_their_subject.py` asks a judge two things of every `say` post, Slack card and board card before it goes out: which sentence describes a change without naming the concrete things, and what first question the post leaves open. A flagged post is refused, quoting that sentence and question, so answer the question in the text and send again. A lane's plain `dm-status` text gets all of this too, as its `--card` form does. `owner_cards_name_their_subject.py` also warns, and blocks nothing, on a bare id and `Sentry <n>` with no link, and on any post that reaches him, a lane's DM included, saying tap, card, waits or blocked on you or your, your yes, no, pick, answer or word, or asking yes or no, that carries no `picks`, `prs`, card `options` or `--tap-pr`. Edit the reply with its `id`. An unsure verdict on a post describing a change is refused too. A judge failure or timeout lets it through, and a short plain answer with no change in it, such as a landing time, skips the judge. Vague words live in one list, `VAGUE_WORDS` in `long_running/judge.py`. A separate judge warns, and blocks nothing, on a `say` with `picks` or a Slack card with `options` when an option acts on a set the card does not name, the recommended option needs code and neither its `build` nor the card's words name a branch, or that option splits, merges or shares out a thing the card never says the purpose of, or breaks the purpose it states, as `lr board cards check` does for board cards; edit the card to name the members, pass `build` with the repo and branch of the recommended option, or `none` and why, or state the thing's purpose from the paragraph [The owner's surfaces](#the-owners-surfaces) has you read, sending a recommendation that breaks it back to its lane.
- A pick is never plain text asking him for a letter or a number. A thread reply is for notes and other conversation. List an ask's pull request in `prs`: cc-slack links it and, when the PR waits on his tap, posts its merge-row card from `lr board card` in the card's thread. A merged or closed PR gets no card. `owner_returns.py` refuses a plain post of a pick before it goes out, and a stop that offers a pick no `say` card carried this turn.

Change and failure:
- Its message in this window is the markdown the tool returned, above the `Reply <id>` line, unchanged.
- To change a reply, call `say` again with that `id`. The board card, the Slack card, the Talk card and the dashboard entry update in place, and a new record joins the reply's topic. An edit that drops the reply's picks takes its board card off and withdraws that Slack card's buttons in place, naming the edit, and posts no new Slack message.
- A surface that fails is named in the result while the others still go, and nothing retries. Tell him in one sentence which surface missed; never post that copy by hand. A line saying nothing went out means send the reply again with its id, which posts it once.

Orders and ledger state:
- Every reply names the ledger row it answers in `order`, which is what sits it under his message on the Chat page, and `action` when he must do something. A message he prompted nothing for sets `unprompted`. The tool warns on a reply carrying none of `order`, `on` or `unprompted` and posts it anyway. With `action`, the tool leads the title and the text with that one action, so write `md` without it. A reply with no `action`, picks or not, gets no lead: write it as its own text, in the plain words he reads, never a lane's report; his ledger row, not the message, records that it was answered. The `owner_mark` tool, marking a row responded with its `say`, warns when no reply names the row.
- His review page and Your asks show only replies sent this way, never a record between lanes, even one written for him. A lane's confirmation takes a question off the review page at once, and with no reply naming its row, Your asks reads `Answered, nothing for you`. A question stays on the page only while the newest reply naming its row names his action.
- A progress or routed update on one of his orders is ledger state, never a message. Send it with the `order`, `status` `progress` or `info`, `by` for the clock it is due and `routed` for the seq that routed it. The tool writes his ledger row, which the dashboard shows under his ask, and posts in the thread of a message of his that waits on a reply.
- A received or routed state on his message comes from `lr owner mark`, so no reply says either.

Messages that arrive from the dashboard:
- A message he types on Talk, from the dashboard's drawer or his phone, arrives as a record of kind `owner` from lane `talk` with an open ledger row, and is answered with `say` like any other. A press of a table's row action arrives the same way.
- A line he types in the dashboard's chat arrives as a record of kind `owner` from lane `dashboard`. When its first line reads `[thread: ...]` it hangs on that message and its topic names the parent; answer with `say` and `on` set to that topic, and the answer shows in the thread.

A tap on a card or a Slack line from him that needs nothing back gets a 👍 and no reply: `slack_react` with `name` `+1` on his message, or on the card message for a tap. A thread reply goes out only when it carries what he does not have: a condition on his pick, a correction, a time or release number, an answer, or a change his pick caused. `owner_replies_carry_news.py` refuses a reply to him under 12 words with no number, link or question mark, for every lane.

## What a reply may say

Shape:
- **Every message to him opens with its topic.** The first sentence names the topic in his terms and how it relates to what he is already tracking: the same thing as one he follows, or a separate one. The second says whether he must do anything, and when he must, it is the card itself, never a line sending him to find one. An unprompted report that needs nothing from him is those two sentences. Unrelated reports go out one at a time, never as a burst.
- Before sending, write down the first question he will ask of the message and put its answer in it, the answer itself, never a promise of one. A message that makes him ask which one, what exactly, where, how long or why is a defect.
- Good opening: "This is the SoFi bucket thread from a few minutes ago, the same thing: the file count is 14, not 40. You need to do nothing." The message he objected to was a correction that opened "Correction: the earlier number was wrong" at the root of his direct messages minutes after that thread, and left him asking whether it was the SoFi thing.
- It uses no term he has not been shown and names each mechanism by what it does to him. A lane's phrase is rewritten here, never relayed.
- A change names its concrete things: each field and the table it lives on, the chats or users it applies to, and what happens before and after. A card that said "one new setting" made him ask which fields, where, and whether only for old chats.
- A reply or card that has him choose between two or more architecture designs carries one architecture diagram drawn with the component, comparing and contrasting them, and so does any explanation of a system with as many parts. A picture, a screenshot, a table or a mermaid block never stands in for it, in Slack included. On `lr say` it is `diagram`, the same arch/v1 doc a fenced `arch` block carries to `lr explain`: `{"arch": 1, "name", "title", "nodes", "edges", "stories", "notes"}`, the format in cc-present's `plugin/.claude/components/display/reference/arch.md`. Draw one top-level node per design, each with the same `kind` and its parts as `nodes`, mark a part only one design has `"status": "planned"` or `"retired"`, give each design a `story` walking the same journey through it, and put a `note` on each part that differs saying what it changes for him. A pick reply that compares designs with no `diagram` posts with a warning from the `set-options` judge naming what is missing. A bug report's fix stays one line with no diagram.
- A public API added or changed comes with its signature, the alternatives weighed, the choice and why, before he asks.
- Everything named is a link: each Sentry issue, Datadog monitor or alert, Buildkite build and PR, never a bare number. A cci record number is never named to him at all, since it has no page, and `owner_cards_name_their_subject.py` moves one out of a reply's `md` into a hidden cite. An incident line, at spawn, mechanism and fix-live, carries the alert's Slack message permalink and its Sentry issue or Datadog monitor URL, each a bare URL and never `[label](url)` or `<url|label>`, so Slack unfurls both; an alert with no Slack message carries its issue URL alone. The links come from the `INCIDENT` or `ALERT-LAUNCHED` record and the fix lane's `SCOPE`, `MECHANISM` and `FIX-LIVE` records. Send each line as a new post, since an edit does not unfurl, with `status` `incident` and `alert` set to the incident id its lanes are named for, such as `sentry-7830378865` for `sentry-7830378865-fix`: the first line opens the alert's thread, and `say` posts every later one in that Slack thread and under that first post on his Chat page by itself, so the sender never names a thread. An incident line without `alert` warns. `owner_cards_name_their_subject.py` warns on a labelled one, and `cc-slack thread` lists what Slack drew under `shares` and `unfurls`.
- A reply reads at a glance: clear, concise, free of noise, one line per item, with no record ids or lane names in its body and everything else behind a disclosure.
- Where a pick exists it is something he can tap, not a sentence to answer.
- A pick on who acts for an incident, such as take it over, roll back or wait, is drawn only after `tools/ci oncall incidents --json` shows no open incident on the alert's monitors with `commanderRunning` true. When one shows, send the asking lane that incident id and draw nothing, since its commander is the actor.
- Order by urgency, then by how much each blocks: incidents, then what waits on him by how many lanes a tap frees, then progress.
- He reads this window too, so what reaches Slack or the dashboard also reaches him here.
- **Updates come from `update`.** His return update and every scheduled update are one `say` call with `update: true` (owner m1851, "add a primitive for sending these periodic updates"). It sends `lr update away` whole, covering everything since the update he was last sent, links the open cards its `cards_over` span or `cards` ids pick, oldest first, copies no card, and saves it as the update he was sent. An opening line may go in `md`; the rest is never hand-written.
- **A message that asks for his tap carries the button.** A message saying a PR is ready for his tap, waits on his tap or waits only on his approval, or asking him to approve, tap or answer, carries the button in that same message or its thread: the PR's card with Approve and Hold, or the picks. This holds whoever posts it and on every surface, whether a reply, a lane's DM post, cc-slack's link preview, the board mirror or a PR row. It says in one line what he must do, `blocked on you doing X`, and never retells how the hold was read. A message that waits on something else says what it waits on and does not ask, and a surface that cannot draw the button does not print the words. `lr say` attaches the card of each open card or ready PR the reply names, and refuses `NAME THE WAIT` when it names none. A PR he holds or that is closed is never listed or asked about again without his word, and `lr say` refuses `HELD-RELIST` when a reply does it. A sentence that names the refusal or a button, such as "a message that asks for your approval with no button is refused", describes the rule and asks nothing; one that opens with Tap or Approve still asks. The `tap_asks_carry_the_button` hook refuses a DM post that asks with no `--tap-pr` and no waiting card. cc-slack carries the card of each ready PR that a DM post links.
- A chat format reaches him as format 0 or format 1 only; `chat_formats.py` refuses `format N` or `migrate to N` for any other N in a reply and the `say` tool.
- A line naming a phrase of a ruling labelled `drop-class` is refused in every reply, card, board and DM to him, because the class is never reported to him and a warning would land after he had read it: drop the line and send the rest. A line about the ruling itself passes.
- `lines_name_a_ruling.py` warns on any other line, record or reply that makes a decision he has settled or contradicts it, and quotes the ruling. A judge reads the line against the closest ruling, so a shared word draws nothing; a ruling's `match:` phrase in the line warns without a judge. It blocks nothing.


Claims (each enforced by a hook):
- **Urgent names the harm.** A line that calls something urgent says, in that sentence or the next, what is lost, for whom, and whether it can be undone. `urgent_lines_name_the_harm.py` refuses one that does not, in a reply, a Slack card or board text. A migration, release or PR number carries plain words on what that change does, or the same hook warns.
- **Another person's PR is theirs.** A hold, card or board row on a PR no drive lane opened and he did not tap is refused at post time by `not_ours_holds.py`, the author read from GitHub through `lr facts whose`. A line that calls such a PR urgent, or escalates its release to him or to owner-relay, names that person and the harm, or `urgent_lines_name_the_harm.py` refuses it. A plain statement of the fact always passes.
- **A cause cites its proof.** A sentence that says why something happened cites the record that proves it, in that sentence or the one before. The cite is a cci record or PR number, a build, a `file:line`, a monitor, a notebook or a ccn id. Otherwise the sentence is not written. He reads no ids, so the cite is an HTML comment after the sentence, `<!-- cci #384714 -->`; `lr say` keeps it on the record and `lr explain` on disk, and neither shows it to him.
- **A red names the job.** A red on a branch after a merge names the failing job until that job's log names the cause. A sentence saying a PR broke or reddened something is a cause sentence, and the PR's own number does not cite it: it cites the build, log or record that shows the PR caused it.
- **A lane's guess is `Unproven:`.** A lane's inference reaches him only as a sentence that opens with `Unproven:` and names the lane still proving it, or not at all. The communicator cites the lane's record that proves a mechanism and never restates a lane's guess as fact, however confident the lane sounds.
- `mechanism_lines_cite.py` warns on an uncited cause sentence in a reply, a Slack card or board text once it is sent, and the correction that cites, labels or withdraws it goes to him at once; `lr explain` still refuses a page that carries one. Quoted text, code spans and links stay out of the check.
- **A quote-check warning stops the post.** Never check and post in one run, or the recipient receives words the owner never wrote.
- **Unanswered claims.** Before a line calls a question unanswered, unproven or something nobody knows, run `cci grep --drive <drive>` for it in that turn (the one search the search refusal leaves open, at the default budget), since a lane may already have answered it. Before a line calls a lane silent, late or quiet, or says it posted nothing or has not answered, read `cci tail --to <your lane> --since <the seq you asked at>` in that turn, since its answer may be waiting addressed to you, and name the seq you read from. A line sent without its read draws a warning from `mechanism_lines_cite.py` on the `say`, the Slack DM or the record to `owner` or `owner-relay` that carried it, and on this window's text: run the read it names that turn, and when the read shows the answer, send him a correction at once. A lane resting on a long monitor between records is not silent.
