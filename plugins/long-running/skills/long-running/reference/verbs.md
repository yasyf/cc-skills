# The drive verbs

Every verb `drive` takes and every flag of each, one row per verb; a test keeps the table equal to
the parser. Read a row with `drive manual verbs "<verb>"`, because it prints the installed row
whole, refusals included. Rows leave out `--drive <name>`, by default this session's drive, and
`--json`; `[ ]` marks what may be left out, `...` what repeats. Read an order, job or PR with
`drive status <id>`, which `drive order show` and `drive job show` print too.

Each verb holds a shared lock on its install until it returns. A newer install's first save of a
drive an older one saved waits for those locks however long the verb runs, about a minute behind a
launch, so no verb meets a `drive.json` saved by code newer than its own and none saves what it did
past one. `drive install` and `drive job prove` hold none, so a newer install's first save never
waits on an update, a release, Homebrew, CI or a proof file; a proof that meets a drive a newer install
saved hands its result to that install's `drive job proved`. A write waits up to five minutes for the drive's own
lock, then refuses and changes nothing, naming the process that holds it. The watch holds none, since the watch on a newer
install posts every line the older one had not. A `drive` started from an older install than the
newest, such as a launch's bind prefix, hands itself to the newest install's `drive` before any verb
acts. A Sprite lane's `drive`, which its launch puts on the Sprite, asks each verb of this Mac as
one Orca question, `DRIVE <its words>` with stdin and each file a word names, and the watch runs it
here, after copying each picture those show by a path on the Sprite into the job's scratch folder over
cc-remote's ssh forward, so a card drawn here opens it: `job report`, `job ask`, `job set --repro`, `job replies`, `job held`, `pr add`, `pr set --flaky`, `plan search`, `manual`
and `status`, each on that lane's own drive alone, its reads on any job as a Mac lane's, a bare
`status` on its own job, and its writes, a `job report` keeping stdin, `job ask`, `job set --repro`,
`pr add` and `pr set --flaky`, on its own job alone, answering all it printed and its exit status, which the lane's
`drive` prints and exits with; `break-glass` it refuses, since its command would run on this Mac as
its user.

## Tool or Bash

- Call a verb's tool on the drive MCP server when it has one, because one call runs every op the
  turn needs; the same verb also runs in Bash. Other verbs run in Bash.
- `heard`, `status` and `search_plan`, which runs `drive plan search`, take the verb's flags as fields, and `record` posts records to the other
  session. `order` (add, set, posted, told), `job` (add, set, brief), `pr` (add, set) and `incident`
  (open, stop, freeze) take `ops`, a list checked whole before any op runs: a call with an op the
  check refuses runs none of them and prints every refused op with its fix, so fix each and send
  the whole call again. Then it runs them in order, printing a line per op. `order` and `job` save
  the drive once for the call, so a refusal while it runs writes nothing either; `pr` and
  `incident` keep each op before a refusal, since `pr add` starts the lander and `incident open`
  and `freeze` start an evidence record and a freeze, and name the ops left unrun.
- Several ops from Bash go as one `drive tool <tool>` call with `{"ops": [...]}` on stdin, never a
  chain of `drive order add` calls, each its own write.
- Each op is one verb, its flags and positionals as its schema's fields, dashes as underscores; an
  op after an add that names no `id` acts on what that add made.
  `drive job set j3 --branch lr-watch --said "pushed"` is
  `job(ops=[{set: {id: "j3", branch: "lr-watch", said: "pushed"}}])`. A job add's `order` may hold
  an order add's fields, adding that order first.
- Every tool takes `dry_run`, which prints each command or record and runs nothing. A tool call
  ends at three minutes, so `drive job launch` and `drive job end` run as background Bash calls.
