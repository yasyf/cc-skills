# The drive verbs

Every verb `drive` takes and every flag of each, one row per verb; a test keeps the table equal to
the parser. Read a row with `drive manual verbs "<verb>"`, because it prints the installed row
whole, refusals included. Rows leave out `--drive <name>`, by default `$CLAUDE_LONG_RUNNING_DRIVE`,
which every process the drive starts carries, else this session's drive, and `--json`; `[ ]` marks
what may be left out, `...` what repeats. Read an order, job or PR with `drive status <id>`, which
`drive order show` and `drive job show` print too.

No verb waits on another install's verbs. A verb refuses to read a drive a newer install saved,
and refuses its save when a newer install saved the drive since it read it. So no verb meets a
`drive.json` saved by code newer than its own, and none saves past one. A launch, a
resume, an end, a proof, a check, a read and a `say` whose post went out refused that way mid-verb hand what they did to the newest
install's `drive job started`, `drive job sent`, `drive job ended`, `drive job proved`,
`drive pr checked`, `drive job answered` or `drive say-finish`, which keeps it, so nothing they did runs twice. A
`drive job launch` or `drive job resume` command refused that way before its worker started runs
again whole on the newest install whatever it changed, such as the wake of an unreachable lane's
Sprite, since it keeps each step once: a lane's death once per dispatch, a held text once under its
Orca request id, and a worker an earlier run started adopted from the receipt its attempt keeps. Any
other verb or MCP call refused that way before it changed anything, a drive row, an event, a post, a
send or any command but a read, runs again whole on the newest install, given the stdin it read; one
that changed something prints the refusal and exits 2. A `say` or record hook refused that way before it changed anything
hands its payload to the newest install's copy of the hook, whose answer is its own. A launch or resume the watch ran as a process
of its own that still refuses, for any reason, also says it in the watch's `EVENT relaunch_refused …`
line, beside its output in the drive's `relaunches.log`. A write waits up to five minutes for the drive's own
lock, then refuses and changes nothing, naming the process that holds it. A `drive` started from an older install than the
newest, such as a launch's bind prefix, hands itself to the newest install's `drive` before any verb
acts, so `drive --root`, which prints the folder of the install it runs, names the newest one, where a
proof file finds its `hooks/` and `lib/`. A Sprite lane's `drive`, which its launch puts on the Sprite, asks each verb of this Mac as
one Orca question, `DRIVE <its words>` with stdin and each file a word names, and the watch runs it
here, after copying each picture those show by a path on the Sprite into the job's scratch folder over
cc-remote's ssh forward, so a card drawn here opens it: `job report`, `job ask`, `job set --repro`, `job replies`, `job held`, `pr add`, `pr set --flaky`, `plan search`, `datadog`, `manual`
and `status`, each on that lane's own drive alone, its reads on any job as a Mac lane's, a bare
`status` on its own job, and its writes, a `job report` keeping stdin, `job ask`, `job set --repro`,
`pr add` and `pr set --flaky`, on its own job alone, answering all it printed and its exit status, which the lane's
`drive` prints and exits with; `break-glass` it refuses, since its command would run on this Mac as
its user.

## Tool or Bash

- Call a verb's tool on the drive MCP server when it has one, because one call runs every op the
  turn needs; the same verb also runs in Bash. Other verbs run in Bash.
- `heard`, `status` and `search_plan`, which runs `drive plan search`, take the verb's flags as fields, and `record` posts records to the other
  session. `order` (add, set, posted, told), `job` (add, set, brief), `pr` (add, set) and `incident`
  (open, stop, freeze) take `ops`, a list checked whole before any op runs: a call with an op the
  check refuses runs none of them and prints every refused op with its fix, so fix each and send
  the whole call again. Then it runs them in order, printing a line per op. `order` and `job` save
  the drive once for the call, so a refusal while it runs writes nothing either; `pr` and
  `incident` keep each op before a refusal, since `pr add` draws his card and `incident open`
  and `freeze` start an evidence record and a freeze, and name the ops left unrun.
- Several ops from Bash go as one `drive tool <tool>` call with `{"ops": [...]}` on stdin, never a
  chain of `drive order add` calls, each its own write.
- Each op is one verb, its flags and positionals as its schema's fields, dashes as underscores; an
  op after an add that names no `id` acts on what that add made.
  `drive job set j3 --branch lr-watch --said "pushed"` is
  `job(ops=[{set: {id: "j3", branch: "lr-watch", said: "pushed"}}])`. A job add's `order` may hold
  an order add's fields, adding that order first.
- Every tool takes `dry_run`, which runs each op through its verb's own checks, refused as the call
  would be, prints each command or record and keeps nothing; an op that reaches a command doing more
  than read, such as a Slack post, stops there, its line naming that command. A tool call
  ends at three minutes, so `drive job launch` and `drive job end` run as background Bash calls.
