# Start or resume

Run this page when a drive starts and after every restart, resume and compaction of any session, because each leaves you knowing only what the disk and your role's block hold.

Everything here runs on your own judgment: the commands, the repository setting, a fresh agent for a job, a restart of a coordinator whose process has exited. One limit holds: do not stop, signal, suspend or close a session you did not start, Orca, a terminal host or anything of unknown ownership, because its work and its agents die with it. Moving a live role's session ends that session, so `drive move` takes the permalink of his message naming it ([migration.md](migration.md#into-an-orca-terminal)).

## Open each session in Orca

cci runs each session in the tmux session named by its alias and resumes it each time Claude Code exits. `cci session attach <alias>` in an Orca terminal shows it, and Orca's sidebar is where he finds each session. A `nohup`, `claude --bg` or other headless start shows nothing in Orca.

`drive manual start` prints the commands below with `<session env>` and `<session settings>` filled. A command still holding either hole starts nothing right.

- `<worktree>` is the drive's checkout, the worktree in the folder `drive-<drive>`. The drive detaches it at its repository's default branch head at each `drive start`, release start, freeze and lane launch, so every repository tool a session or its agents run from it reads that head. Add a repository Orca does not list with `orca repo add --path <its main checkout>`.
- The first line names the worktree after the drive in Orca's sidebar. Each `cci session register` line starts one session under its alias with the cci subscription its role reads. The last line shows a session in Orca, `<alias>` being the alias it registered, such as `<drive>-coordinator`.
- The fourth line starts the meta session, which holds drive tooling. `drive start` for any role runs it and its `orca terminal create` itself while no meta session is bound, so run them by hand only when that start printed that the meta session did not start.
- The fifth starts a sub-coordinator, the coordinator session for one project beside the top, once an order is filed under `<project>`, or for one order alone under the seat `Priority <o>`, which `drive order set <o> --priority` starts with its `orca terminal create` itself. `<lane>` is that name lowercased, each run of other characters a dash: `Billing` is `billing`, `Priority o2046` is `priority-o2046`.

```sh
orca worktree set --worktree path:<worktree> --display-name <drive>
cci session register <drive>-coordinator --new --drive <drive> --reader root --cursor coordinator --notify meta --batch-kinds done,evidence --mute-kinds report,opened,head --cwd <worktree> --command "<session env> claude -n <drive>-coordinator --model claude-fable-5-2 --effort high --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the coordinator: run Start or resume for that role'
cci session register <drive>-communicator --new --drive <drive> --reader communicator --cursor communicator --notify root,meta --batch-kinds done,report --mute-kinds opened,head,disconnect,recovered --cwd <worktree> --command "<session env> drive advised --drive <drive> --lane communicator claude -n <drive>-communicator --model claude-opus-5-5 --advisor fable --effort high --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the communicator: run Start or resume for that role'
cci session register <drive>-meta --new --drive <drive> --reader meta --cursor meta --notify root --mute-kinds opened,head --cwd <worktree> --command "<session env> drive advised --drive <drive> --lane meta claude -n <drive>-meta --model claude-opus-5-5 --advisor fable --effort high --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox" --resume-prompt '/long-running <drive> as meta: run Start or resume for that role'
cci session register <drive>-<lane> --new --drive <drive> --reader <lane> --cursor coordinator-<lane> --notify meta --batch-kinds done,evidence --mute-kinds report,opened,head --cwd <worktree> --command "<session env> drive advised --drive <drive> --lane <lane> claude -n <drive>-<lane> --model claude-opus-5-5 --advisor fable --effort high --permission-mode bypassPermissions --settings <session settings> <lane rules> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the sub-coordinator for <project>: run Start or resume for that role'
cci session register <drive>-<lane>-communicator --new --drive <drive> --reader <lane>-communicator --cursor communicator-<lane> --notify meta --batch-kinds done,report --mute-kinds opened,head,disconnect,recovered --cwd <worktree> --command "<session env> claude -n <drive>-<lane>-communicator --model claude-opus-5-5 --effort high --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the communicator for <project>: run Start or resume for that role'
orca terminal create --worktree path:<worktree> --title <alias> --command "cci session attach <alias>" --json
```

What the launch lines set, per session, at launch:

- Models. The top coordinator runs Fable 5.2. The communicator, the meta session and each sub-coordinator run Opus 5.5 with Fable 5.2 as advisor, through `drive advised`, which asks a `claude -p --advisor fable` that makes no model call whether Claude Code takes the advisor, then execs the line's `claude`. Claude Code exits at launch on an advisor it refuses, such as Fable before the account's one-time usage-credits consent, and cci would restart it on every exit. So on a refusal `drive advised` starts the session without the advisor, prints the refusal and sends the meta session a `defect` record naming the seat, once a day per seat. Running `/model fable` once in any session and accepting the consent clears it for the seat's next start.
- `<session env>` is `env` with every variable in the orca plugin's `lib/lane.json`, so a session starts as lightly as an Orca lane. `DISABLE_AUTOUPDATER=1` is one, and the `claude daemon` and the spares its `claude --bg` starts inherit it.
- Compaction: the coordinator, the meta session and each sub-coordinator at 400,000 tokens, the communicator at 300,000, every watchdog and lane at the 350,000 of `lib/lane.json`.
- `<session settings>` is one `--settings` value, because Claude Code keeps only the last one and drops an invalid one whole. `agents.session_settings` builds it from `lib/lane.json`, this Mac's `CLAUDE_LANE_SETTINGS` over that, then `SESSION_SETTINGS` in `lib/drive/agents.py`; `drive start` uses it.
- Those settings keep a context small: a Bash result over 6,000 characters comes back as its first 2 KB and the path of the whole, the narrate-after-silence reminder is off, and `outputStyle` `default` overrides the repository's own output style and its per-call reminder.
- No session has the AskUserQuestion tool, because a question there waits in a terminal he does not read. A question for him is a question card ([A question for him](scope.md#a-question-for-him)).
- The Datadog plugin stays on, over a `CLAUDE_LANE_SETTINGS` that turns it off for Orca lanes. Its MCP is a drive session's one Datadog read, since the `bash_guard` hook refuses `pup` there.
- A sub-coordinator runs without `~/.claude/CLAUDE.md`. It loads the plugin's `lane-rules/CLAUDE.md` through the `--add-dir` that fills `<lane rules>`, as each watchdog does.

Ten seconds after a create, `orca terminal show --terminal <the handle the create printed> --json` should read `"orphaned": false`; Orca draws a new terminal for about five seconds, so an earlier read tells you nothing. `"orphaned": true` means Orca dropped the terminal because it hides the worktrees it did not make for this repository, even while `orca worktree show` still finds the worktree. The repository's setting shows it with no restart: `orca repo set --repo path:<main checkout> --external-worktree-visibility show`. It changes what his Orca sidebar lists, so run it for the drive's own repository and tell him you did.

## The line that says where he opens a session

Each session's `drive start` ends with that role's line, a sub-coordinator's opening `sub-coordinator for <project>`. `drive status` prints the line for each role and sub-coordinator, and changes nothing.

The line is read live from Orca's terminals and ptys: it finds the terminal whose process tree holds the session's Claude Code process, or a `cci session attach` client of its tmux session, and reads `open it with: orca terminal switch --terminal <handle>` for the first one Orca reads `"orphaned": false` for. Take the switch command you give him from that line, since it is the one checked against what Orca shows. A hook refuses a post with a switch command naming a terminal no session of the drive runs in.

Any other line carries no switch command. Tell him what it says and act on it:

- `not visible in Orca, which hides the worktrees it did not make for this repository`: every terminal running the session is orphaned. The repository setting above shows it with no restart. `drive start` runs it for the drive's own repository and says so, and `drive status` prints it.
- `in no Orca terminal`, tmux included: the session moves into a fresh Orca terminal by [migration.md](migration.md#into-an-orca-terminal).

When the coordinator's Claude Code process has exited, the drive's watch sends the communicator one `DOWN` line within a minute, naming the session and its folder. The communicator restarts it at once with step 5 of [migration.md](migration.md#into-an-orca-terminal). A project's watch does the same for its sub-coordinator.

## What a compaction keeps

- The `PreCompact` hook has the summary keep only what the disk does not hold: what the session's row of [Each session](#each-session) names, within that row's size.
- The `SessionStart` hook then prints the role's block: its role, channels, rules and where to read the rest, without the orders, jobs or PRs. A sub-coordinator's names its project, the top, the communicator, its cci lane and `Hold no Slack channel`.
- Claude Code also brings back the five files last read or written, each loaded skill body cut at about 20,000 characters, and every loaded tool, so load a tool for the step that needs it.
- Each file Read, Write or Edit opens comes back after every compaction, so the `no_file_tools` hook refuses those three in a drive session, the communicator's reads aside, since it answers him from what it reads. It also refuses a Bash call that reaches a memory file (use `ccn note add`) or `cat`s a whole saved output into the session (use `tail -c 2000 <file>`).
- A page in Claude Code's plugin cache can be older than the install, so a hook refuses reading one there. `drive manual <page> <row>` prints a page, `drive job report <j>` a job's return, and cci a record.
- A skill body comes back as the session first loaded it until a restart. The role's block names the long-running version installed now, so follow the block where the two disagree.

## Steps for each role

1. Check the model, then bind the role:
   - A session runs the wrong model when it differs from its `cci session register` line, or when its `drive status` line adds `runs <model> on Claude Code <version>, which has no entry for that model`. The fix is a restart on the installed build by [migration.md](migration.md#into-an-orca-terminal). `/model` does not fix it: a build older than its model silently runs it at a 200k window, and the session then compacts every few minutes.
   - `drive start <name> --role <communicator, coordinator or meta> [--watch <channel id>]...` creates the drive or binds this role to this session, registers the session with cci by its line above less `--new`, its `--cwd` the drive's checkout, then prints the role's block and line.
   - A session that ran outside cci, or outside the drive's checkout, keeps running where it is until it exits; cci then resumes the same conversation in its tmux session in the checkout, and `drive start` says so. The next install's reload, or `drive reload`, ends it once idle so it resumes there then, and opens the `orca terminal create` line above for one that ran outside cci's tmux. Watchdog agents start in the checkout wherever the session beside them runs.
   - His DM is the communicator's. Each alert channel the drive reads is a `--watch`, kept across restarts and held by the top coordinator; a later `--watch` adds one. His own words in such a channel reach the communicator.
   - A seat's communicator runs `drive start <name> --role communicator --project <project>`, `<project>` being the project or the priority seat `Priority <o>` its resume prompt names. It binds this session as the communicator holding that seat's channel alone, paired with that seat's sub-coordinator, which its owner records reach by default, by his words (in the team-lead session a3327a7a, 1:03 AM Nov 16) "every project has a communicator to pair with its coordinator and messages in that channel should go to it"; the drive's communicator lets that channel go at its next call. The drive's watch starts it on the line after the sub-coordinator's above the first time a message of his is owed in that seat's channel, and `drive order set <o> --priority` starts a priority seat's at once, on Opus at high effort, compacting at 300k like the drive's communicator. The watch retires it after two hours with no message of his owed there, or once its priority order closes. A seat with no sub-coordinator pairs it with the top coordinator. It refuses a seat whose channel the drive keeps none of, and a session holding another role or seat.
   - A sub-coordinator runs `drive start <name> --role coordinator --project <project>`. It binds this session for that project beside the top, replacing any session bound for it, loads the drive's watch, which runs the project's passes, and prints its block. It refuses a project no order is filed under, naming those in use, a session holding a role or another project, and a lane already taken: another sub-coordinator's, one of the drive's own such as `root`, one its records were posted as, or one ending in `-<digits>`.
2. Hold every channel the block's `Hold with` line names, each with no thread; the meta session holds none.
   - His DM and each private channel of the drive, those `drive channels --make` and `say` made: `slack_watch(channel_id=<id>)`.
   - Each coordinator channel: `cc-slack subscribe --kind alerts,releases,posts --channel <id>` in Bash, which delivers one line per alert, release state or top-level post. Subscribing a channel the session already watches turns that watch into the subscription.
   - One session holds a channel at a time. A channel another session holds becomes yours after that session runs `cc-slack unfollow` ([migration.md](migration.md)).
3. Run `cci drive use <name>`. The session's alias already owns the subscription its `cci session register` line sets, a sub-coordinator's reading its lane at cursor `coordinator-<lane>`, and cci refuses a registered session `cci subscribe`.
   - Every record addressed to a session's lane reaches it whatever its kind: root's `go` and `hold`, a refused `ask`'s `refuse` and the watch's `handoff` included.
   - `--batch-kinds` delivers its kinds together, at most every five minutes: `done` and `evidence` for a coordinator, `done` and `report` for the communicator, since the watch starts the post of every `POST` report itself.
   - `--notify` names who hears a session's channel disconnect and recover: the meta session for each coordinator and each seat's communicator, root for the meta session, never a communicator, whose input is his words alone; a communicator also mutes the `disconnect` and `recovered` records not addressed to it.
   - `--mute-kinds` drops from the channel the records of its kinds not addressed to the lane, which `cci tail` still reads. `ccx vcs ship` posts each push's `head` record to nobody, and the watch already sends each coordinator a `new head` line for the PRs of the orders it hears.
   - Each role's `drive start`, and the `SessionStart` hook at each start of its session, compactions included, register the session again by its line less `--new`, so the subscription holds after every compaction.
   - The named cursor resumes where the role's last session stopped, and each channel replays what that cursor missed, so a record sent while the session was down arrives now.
4. The communicator handles each reply `cc-slack dm-owed` lists as a message of his that just arrived, once its `holder_session` is this session. He wrote them while no session held his DM or the operator channel he wrote in. While another drive's communicator holds his DM, those replies are that drive's.
5. The coordinator resumes its work:
   - Its `drive start`, and the `SessionStart` hook at each coordinator session start, load the watch's launch agent unless one is loaded. A sub-coordinator's load the same agent, whose watch runs each project's passes in its one process and posts their lines to `<lane>@<drive>`.
   - The agent starts its watch again on the newest install within 10 seconds of any exit, so a `WATCH stopped` line needs no `drive watch` from you and the watch needs no `Monitor`.
   - The lines each stage of a pass makes for the session arrive as one record: a `handoff` when any line asks a step now, else `evidence` that arrives with others at most every five minutes. A record of several lines counts them by first word, as `35 lines: 35 ORPHAN`, and carries every line in its body.
   - State is on disk: `drive status`, records and cc-notes. A compaction brings back no page, and `drive manual <page> <row>` prints the one you want. Check a fact in the turn you tell it to him.
   - A restart ends every background agent. A codex job's codex-ask run survives, since it runs no agent. A job whose agent is gone, which its order's `ORPHAN` line in `drive status` names, gets a fresh one when something needs it: a `running` job now, a `waiting` job when its next event arrives.
   - Give the fresh agent what the last one knew with `drive job brief <j>`: the earlier brief's `--serves`, `--done-when` and `--where`, any `--ruling <answer id>`, and `--handoff` with the branch, PR and last `said` line. The verb writes his order's and each ruling's words into the brief. The fresh agent's first step moves the job onto it.
   - A ruling a summary carries as an id or a question title reads whole with `cc-notes answer show <id>`: the title is the question, and his answer is in the body.
6. The top coordinator runs `drive dashboard`, which starts the drive's dashboard under its launch agent, finds it running there, or replaces one no agent keeps or one serving other addresses. The agent starts it again 10 seconds after it exits. Its first link is for his phone or laptop: HTTPS on this machine's full tailnet name when the tailnet issues certificates, else HTTP on its bare MagicDNS label; loopback follows. It listens on loopback and this machine's own tailnet addresses, not on a wildcard address, the LAN or Funnel.

A drive saved by the earlier one-session driver reads as that session coordinating; [migration.md](migration.md#from-one-driver-to-two-sessions) moves it to two.
