# Start or resume

Start both sessions in their own Orca terminals with these three commands—never in a bare tmux session, `nohup`, `claude --bg` or any other headless start—so he finds both in Orca's sidebar and opens either with one command. `<worktree>` is the drive's checkout, or the monorepo checkout's root for a monorepo drive; if Orca does not list the repository, add it first with `orca repo add --path <its main checkout>`.

```sh
orca worktree set --worktree path:<worktree> --display-name <drive>
orca terminal create --worktree path:<worktree> --title <drive>-coordinator --command "claude -n <drive>-coordinator --model claude-fable-5-2 --effort xhigh --permission-mode bypassPermissions --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack -- '/long-running <drive> as the coordinator: run Start or resume for that role'" --json
orca terminal create --worktree path:<worktree> --title <drive>-communicator --command "claude -n <drive>-communicator --model claude-fable-5-2 --effort xhigh --permission-mode bypassPermissions --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack -- '/long-running <drive> as the communicator: run Start or resume for that role'" --json
```

Check each terminal 10 seconds after creation with `orca terminal show --terminal <the handle the create printed> --json` (Orca draws every new terminal for about 5 seconds, and `orca worktree show` still finds hidden worktrees). It must read `"orphaned": false`. If it reads `"orphaned": true`, Orca hid a worktree it did not create; run `orca repo set --repo path:<main checkout> --external-worktree-visibility show` for the drive's repository alone and tell him, rather than restarting.

For a new drive, the coordinator's prompt ends `; his DM is <channel id>`, which its `drive start` passes as `--channel`. `drive start` records the session's Orca terminal and prints its proof line (`drive status` prints both roles' lines read-only). Once `orca terminal show` reads `"orphaned": false` and the terminal's process tree holds the session's Claude Code process (`~/.claude/sessions/<pid>.json`), the line reads `open it with: orca terminal switch --terminal <handle>`. Give him a switch command from that line alone; report any other line in its own words with no switch command:

- `not visible in Orca, which hides the worktrees it did not make for this repository`: `drive status` prints the repository setting above; `drive start` runs it for the drive's repository and tells him.
- `not visible in Orca until restarted into a terminal` (where the terminal's process tree no longer holds the session) or `in no Orca terminal`, tmux included: move the session into a fresh Orca terminal by [reference/migration.md](migration.md#into-an-orca-terminal) only on his word.

Each session then runs the steps below on start, restart, resume or compaction. To keep context minimal, `PreCompact` keeps only state not on disk: for the communicator, each handler still out and each acked message of his with no handler yet (at most 1,500 characters); for the coordinator, each unrecorded operation it owns, his words not yet in an order or answer, and its current step (at most 3,000). `SessionStart` then prints the role's block—its role, what it holds, its rules, one line per order owing a promised line for the coordinator, and the reads for the rest (`drive status`, `drive view`, `cci digest`)—staying under Claude Code's 10,000-character hook cap. Because Claude Code reloads the last five files touched, loaded skill bodies and every loaded tool on compaction, load a tool only for the step that needs it, read `drive manual` pages, and never read or write files with Read, Write or Edit (the hook denies them). Because a live process keeps the skill body it first loaded until restart, the role's block names the installed version and wins wherever they disagree.

1. Run `drive start <name> --role <communicator or coordinator> [--channel <his DM id>] [--watch <channel id>]...` to create the drive or bind that role to this session and its Orca terminal, printing the role's block and proof line. The communicator holds his DM (`--channel`) and receives his words in any channel; the coordinator holds each alert channel (`--watch`, persisted across restarts; later `--watch` flags add channels). Never switch a live session's model with `/model`, and because a Claude Code build older than its model runs it at a 200k window, move a session on another model or an older build in `drive status` into a fresh Orca terminal by [reference/migration.md](migration.md#into-an-orca-terminal) only on his word.
2. Hold every channel on the block's `Hold with` line with no thread: `slack_watch(channel_id=<id>)` for his DM, and `slack_subscribe(channel_id=<id>, kinds=["alerts", "releases", "posts"])` for each coordinator channel (which converts an existing watch on that channel). Because only one session holds a channel at a time, another session must run `cc-slack unfollow` before you take its channel ([reference/migration.md](migration.md)).
3. Run `cci drive use <name>`, then the block's `Subscribe:` line: `cci subscribe --reader communicator --cursor communicator`, or `cci subscribe --reader root --cursor coordinator` with `--to-kind` adding `refuse` so a refused `ask` wakes the coordinator. The named cursor resumes where the role's last session stopped.
4. In the communicator, handle each reply `cc-slack dm-owed` lists by its table, sent while no session held his DM.
5. In the coordinator, arm `Monitor` with `drive watch` (`timeout_ms` 1800000) and re-arm it on every expiry notice (a duplicate or communicator copy exits on its own), then read `drive status`. Because a restart ends background agents, start a fresh agent only when needed—now for a `running` job, or on the next event for a `waiting` job—with a handoff brief carrying the branch, PR, last `said` line, and the earlier brief's `Order`, `Serves` and `Decisions that bind` in his words rather than an answer id. Never re-derive state from memory; read any compacted ruling whole with `cc-notes answer show <id>` before acting on it, because the title is only the question.
6. In the coordinator, run `drive dashboard` to start, find or replace the dashboard and print its bare MagicDNS tailnet and loopback links; it listens only on loopback and this machine's tailnet addresses, never the LAN or Funnel.

A drive saved by the earlier one-session driver reads as that session coordinating; move it to two sessions by [reference/migration.md](migration.md#from-one-driver-to-two-sessions).
