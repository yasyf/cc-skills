# Start or resume

Run this page when a drive starts and after every restart, resume and compaction of any session, because each leaves you knowing only what the disk and your role's block hold.

- No word from him is needed for this page's commands, the repository setting below, running `drive watch` again, a fresh agent for a job, or restarting a coordinator whose process has exited.
- Moving a live session into a fresh Orca terminal, onto another model or build included, needs his word naming that session.

## Open each session in Orca

1. Register each session with cci, which runs it in the tmux session named by its alias and starts it again, resuming it, each time Claude Code exits, then show it in an Orca terminal of its own with `cci session attach <alias>`, because he finds each in Orca's sidebar and opens it with one command. A `nohup`, `claude --bg` or other headless start shows nothing in Orca. His pick lifts the ban on `claude --bg` for handlers only, which `drive handler` starts that way: "drive handler starts each as a claude --bg session that ends by posting one cci line: compacting every 6.5 hours, 1.6 GB while one runs".
2. Whoever starts the drive runs them as `drive manual start` prints them, which fills `<session env>` and `<session settings>` in each; a command still holding either hole starts nothing right. `<worktree>` is the drive's checkout, the monorepo checkout's root for a monorepo drive; add a repository Orca does not list first with `orca repo add --path <its main checkout>`. The first command names the worktree after the drive in Orca's sidebar. Each `cci session register` line after it starts one session under its alias, with the cci subscription its role reads, and the last line shows it in Orca, `<alias>` being the alias it registered, such as `<drive>-coordinator`. The fourth line starts the meta session, which holds drive tooling: every drive has one, and `drive start` for any role runs it and its `orca terminal create` itself while no meta session is bound, by his words "have the skill always start a meta root as a sibling to coordinator and communicator", so run them by hand only when that start printed that the meta session did not start. The fifth starts a sub-coordinator, the coordinator session for one project beside the top, once an order is filed under `<project>`; `<lane>` is that name lowercased, each run of other characters a dash (`Iris` is `iris`).

```sh
orca worktree set --worktree path:<worktree> --display-name <drive>
cci session register <drive>-coordinator --new --drive <drive> --reader root --cursor coordinator --to-kind incident,mechanism,fix-live,decide,ask,design,blocker,blocked,urgent,answer,release,correction,owner,refuse,handoff --batch-kinds done,evidence --mute-kinds report,opened --cwd <worktree> --command "<session env> claude -n <drive>-coordinator --model claude-fable-5-2 --effort xhigh --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the coordinator: run Start or resume for that role'
cci session register <drive>-communicator --new --drive <drive> --reader communicator --cursor communicator --notify root,meta --cwd <worktree> --command "<session env> claude -n <drive>-communicator --model claude-opus-5-5 --effort xhigh --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the communicator: run Start or resume for that role'
cci session register <drive>-meta --new --drive <drive> --reader meta --cursor meta --cwd <worktree> --command "<session env> claude -n <drive>-meta --model claude-opus-5-5 --effort xhigh --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox" --resume-prompt '/long-running <drive> as meta: run Start or resume for that role'
cci session register <drive>-<lane> --new --drive <drive> --reader <lane> --cursor coordinator-<lane> --to-kind incident,mechanism,fix-live,decide,ask,design,blocker,blocked,urgent,answer,release,correction,owner,refuse,handoff --batch-kinds done,evidence --mute-kinds report,opened --cwd <worktree> --command "<session env> claude -n <drive>-<lane> --model claude-fable-5-2 --effort xhigh --permission-mode bypassPermissions --settings <session settings> --channels plugin:cc-inbox@cc-inbox plugin:cc-slack@cc-slack" --resume-prompt '/long-running <drive> as the sub-coordinator for <project>: run Start or resume for that role'
orca terminal create --worktree path:<worktree> --title <alias> --command "cci session attach <alias>" --json
```

3. Each session starts as lightly as an Orca lane, by his words "the lanes doner need any update cghecks or anything realy that is nrotlly needed for "iunteractive" sessionms" and "we were supposed to pass the env vas in long-running to disable those": `<session env>` is `env` with every variable in the orca plugin's `lib/lane.json`, the file `orca-worker-launch.sh` reads. `DISABLE_AUTOUPDATER=1` is one, so the session skips the plugin auto-update pass, and so do the `claude daemon` and spares its `claude --bg` starts, which inherit its env. `<session settings>` is one `--settings` value, because Claude Code keeps only the last one and drops an invalid one whole. It holds that file's settings and denied tools, this Mac's `CLAUDE_LANE_SETTINGS` over them, then the drive's own below. `agents.session_settings` builds it, the same function `drive start` uses for the meta session and `drive handler` for each handler. The session keeps its tools and runs interactive, never `-p`.
4. `--settings` keeps each context small: a Bash result over 6,000 characters comes back as its first 2 KB and the path of the whole, and the reminder to narrate after silent turns is off, since nobody reads a drive's terminals. `outputStyle` `default` overrides the repository's own output style, such as `Concise`, whose reminder Claude Code attaches to about half of a session's model calls: 8,500 tokens an hour in the communicator, 10,400 in the coordinator. Its `permissions.deny` takes the AskUserQuestion tool out of the session, by his words "we aare supposed to launch the coordinator etc with no askuserquestion tool": a question there waits in a terminal he never reads, so every question for him reaches him as a question card ([A question for him](scope.md#a-question-for-him)). Its `enabledPlugins` keeps the Datadog plugin on, merged over `CLAUDE_LANE_SETTINGS` plugin by plugin, since that variable turns the plugin off for Orca lanes and the Datadog MCP is a drive session's one Datadog read: the `bash_guard` hook refuses `pup` in every drive session. These are `SESSION_SETTINGS` in `lib/drive/agents.py`, which `drive start` passes the meta session and `drive handler` each handler.
5. Ten seconds after each create, check that `orca terminal show --terminal <the handle the create printed> --json` reads `"orphaned": false`. Orca draws a new terminal for about five seconds, so an earlier read proves nothing.
6. `"orphaned": true` means Orca dropped the terminal because it hides the worktrees it did not make for this repository; `orca worktree show` still finding it proves nothing. Fix it with the repository's setting, never a restart: `orca repo set --repo path:<main checkout> --external-worktree-visibility show`. Every session keeps running, and its terminal reads `"orphaned": false` once it is set.
7. Run that setting for the drive's own repository only, and tell him you ran it, because it changes what his Orca sidebar lists.

## The line that says where he opens a session

1. Each session's `drive start` records the Orca terminal it runs in, under tmux the one that last ran `cci session attach` for it, and ends with that role's line, a sub-coordinator's opening `sub-coordinator for <project>`; `drive status` prints the line for each role and each sub-coordinator, and changes nothing.
2. The line reads `open it with: orca terminal switch --terminal <handle>` only once Orca reads `"orphaned": false` for the terminal and its process tree holds the Claude Code process whose `~/.claude/sessions/<pid>.json` names the session.
3. Give him a switch command only from that line, never from a create's output, an environment variable or a record, because only the line is checked against what Orca shows; a hook refuses a switch command naming a terminal neither role runs in, a sub-coordinator's included.
4. Any other line carries no switch command. Tell him what it says in its own words, and act on it:
   - `not visible in Orca, which hides the worktrees it did not make for this repository`: the repository setting above shows it with no restart; `drive start` runs it for the drive's own repository and says so, and `drive status` prints it.
   - `not visible in Orca until restarted into a terminal` (Orca shows the terminal, but its process tree no longer holds the session) or `in no Orca terminal`, tmux included: move the session into a fresh Orca terminal by [migration.md](migration.md#into-an-orca-terminal), on his word.
5. When the coordinator's Claude Code process has exited, the drive's watch sends the communicator one `DOWN` line within a minute, naming the session and its folder, and the communicator starts a handler that restarts it at once with step 5 of [migration.md](migration.md#into-an-orca-terminal), whose terminal starts its tmux session again where cci session run resumes it, and tells him it did. A project's watch does the same for its sub-coordinator. He ruled that a coordinator that is down is restarted, never only reported.

## What a compaction keeps

1. He ruled that a compaction leave minimal context and the state on disk stay compact, so the `PreCompact` hook has the summary keep only what the disk does not hold:
   - each session keeps what its row of [Each session](#each-session) names, at most 1,500 characters for the communicator and the meta session and 3,000 for the coordinator.
2. The `SessionStart` hook then prints the role's block: its role, channels, rules, the coordinator's owed promised lines, and where to read the rest, never the orders, jobs or PRs. A sub-coordinator's names its project, the top, the communicator, its cci lane and `Hold no Slack channel`, and only its project's owed lines.
3. Claude Code also brings back the five files last read or written, each loaded skill body cut at about 20,000 characters, and every loaded tool, so load a tool only for the step needing it.
4. The `no_file_tools` hook refuses Read, Write and Edit in a drive session, because each file they open comes back after every compaction, and a Bash call that reaches a memory file (use `ccn note add`) or `cat`s a whole saved output into the session rather than a file (use `tail -c 2000 <file>`). A hook refuses a read of a page in Claude Code's plugin cache, which can be older: read a page with `drive manual <page> <row>`, a job's return with `drive job report <j>`, and a record with cci.
5. A skill body comes back as the session first loaded it until a restart, whatever was installed or loaded since. The role's block names the long-running version installed now, so follow the block where the two disagree.

## Steps for each role

Each role runs its steps here in order.

1. Check the model, then bind the role:
   - When a session runs a model other than its `cci session register` line names, or its `drive status` line adds `runs <model> on Claude Code <version>, which has no entry for that model`, restart it on the installed build by [migration.md](migration.md#into-an-orca-terminal), on his word. Change a live session's model only this way, never with `/model`, because a build older than its model silently runs it at a 200k window and the session then compacts every few minutes.
   - `drive start <name> --role <communicator, coordinator or meta> [--watch <channel id>]...` creates the drive or binds this role to this session and its Orca terminal, registers the session with cci by its line above less `--new`, then prints the role's block and line. A session that ran outside cci keeps running where it is and moves into its tmux session once it exits; `cci session attach <alias>` shows it there.
   - His DM is the communicator's. Each alert channel the drive reads is a `--watch`, kept across restarts and held by the top coordinator; a later `--watch` adds one. His own words in such a channel reach the communicator, never the coordinator.
   - A sub-coordinator runs `drive start <name> --role coordinator --project <project>`, which binds this session for that project beside the top, replacing any session bound for it, starts the project's watch and prints its block. It refuses a project no order is filed under, naming those in use, a session holding a role or another project, and a lane already taken: another sub-coordinator's, one of the drive's own such as `root`, one its records were posted as, or one ending in `-<digits>`.
2. Hold every channel the block's `Hold with` line names, none for the meta session, each with no thread: his DM with `slack_watch(channel_id=<id>)`, and each coordinator channel by running `cc-slack subscribe --kind alerts,releases,posts --channel <id>` in Bash, which delivers one line per alert, release state or top-level post. Subscribing a channel the session already watches turns that watch into the subscription. One session holds a channel at a time, so a channel another session holds becomes yours only after that session runs `cc-slack unfollow` ([migration.md](migration.md)).
3. Run `cci drive use <name>`, and no `cci subscribe`, which cci refuses a registered session: its alias owns the subscription its `cci session register` line sets, a sub-coordinator's reading its lane at cursor `coordinator-<lane>`. The coordinator's `--to-kind` list includes `refuse`, so a refused `ask` wakes it, and `handoff`, the watch's lines it acts on now, with `--batch-kinds done,evidence` for the rest, and `--mute-kinds report,opened` drops the drive's `opened` and `report` broadcasts from its channel, though `cci tail` still reads them. The named cursor resumes where the role's last session stopped, and each channel of a registered session replays what that cursor missed, so a record sent while it was down arrives now.
4. The communicator handles each reply `cc-slack dm-owed` lists as a message of his that just arrived, because he wrote them while no session held his DM.
5. The coordinator resumes its work:
   - Its `drive start`, and the `SessionStart` hook at each coordinator session start, compactions included, load the watch's launch agent unless one is loaded, whose records the session's registered subscription reads; a sub-coordinator's load its project's watch's agent, and that watch posts to `<lane>@<drive>`. The agent starts its watch again on the newest install within 10 seconds of any exit, a crash or a newer install's included. A line it acts on now arrives as a `handoff` record, the rest as `evidence` records together at most every five minutes. Arm no `Monitor` for it, and run no `drive watch` for a `WATCH stopped` line.
   - Read `drive status`, and take state from it, records and cc-notes, never from memory, because the disk is the record.
   - After a compaction, run the `drive manual <page> <row>` your summary names for its step before acting, because a compaction brings back no page.
   - A restart ends every background agent. A job whose agent is gone gets a fresh one only when something needs it: a `running` job now, a `waiting` job when its next event arrives.
   - Write its brief with `drive job brief <j>`, passing the earlier brief's `--serves`, `--done-when`, `--where` and each `--ruling <answer id>`, plus `--handoff` with the branch, PR and last `said` line; the verb writes his order's and each ruling's words whole. The fresh agent's first step moves the job onto it, since the brief's `Drive` line names the job and the agent that held it ended with its session.
   - When a ruling comes back after a compaction as an id or a question title, read it whole with `cc-notes answer show <id>` before anything acts on it: the title is the question, and his answer is in the body.
6. The top coordinator runs `drive dashboard`, which starts the drive's dashboard under its launch agent, finds it running there, or replaces one no agent keeps or serving other addresses; the agent starts it again 10 seconds after it exits. Its first link is for his phone or laptop: HTTPS on this machine's full tailnet name when the tailnet issues certificates, else HTTP on its bare MagicDNS label; loopback follows. It listens on loopback and this machine's own tailnet addresses only, never a wildcard address, the LAN or Funnel.

A drive saved by the earlier one-session driver reads as that session coordinating; [migration.md](migration.md#from-one-driver-to-two-sessions) moves it to two.
