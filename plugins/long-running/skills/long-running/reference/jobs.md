# Jobs

Every job is the coordinator's except a drive tooling builder, which is the communicator's under [Tooling](communicator.md#tooling) (`drive job add` refuses a job on a "Drive tooling:" order from the coordinator's session). Before starting a Forge-AI/monorepo builder, run `drive place`: it answers `remote` when this Mac's CPU is at or over its load gate's limit or when eight builders already run here, and `local` otherwise. A `remote` monorepo builder starts as a remote lane on a Sprite, where builds and checks run on that machine; past eight local builders, any non-monorepo builder waits as `open`, oldest due first. Readers, codex jobs, builders on other repositories (since a yasyf/* tool installs on this Mac), jobs touching this Mac's processes, and handoffs whose `PROVE:` line runs `ci mac-box` or `ci devbox` always run here because a Sprite has no AWS sign-in and both verbs use this Mac's `DEVBOX_AWS_PROFILE`.

**On this Mac.**
1. Add the job first with `drive job add <kind> --order <o> --goal "<one line>" [--part "<part>"]...` so the brief's `Drive:` line names it; drive records the started agent on that job and marks it `running` again on each `SendMessage`.
2. Start the job with the Agent tool: `subagent_type` `long-running:builder`, `long-running:reader` or `codex:codex-wrapper`, `run_in_background: true`, a short `description`, and the brief as `prompt`, plus `model: "sonnet"` for a reader only when its question is a one-fact lookup (research or judgment calls use Opus; a design lane's call is in [Design first](design.md)). Omit `name`: agent teams are on here, and a named agent becomes a teammate that never wakes on events. The `agent_brief` hook denies a coordinator's or communicator's Agent call that names the agent, puts any agent but `long-running:designer` on a Fable model, or starts a `long-running:builder` without a `Serves:` or `Handoff:` line.
3. The line the agent returns, or the first line piped to `drive job report <j> -`, sets the job's state and said line: `DONE` and a reader's answer mark it done, `READY`, `WAITING` and `DESIGN` mark it waiting, and `BLOCKED` marks it failed; `drive job ask` sets `ASK`, and only `BUILT` is recorded by hand with its branch and cards. The watch reads the agent's transcript rather than stored state: a `running` job whose agent ended its turn, wrote nothing for 30 minutes, or belonged to an earlier session makes its parts `ORPHAN`s.

**Remote.**
1. Run `drive job add builder --order <o> --goal "<one line>" --remote`, then from the monorepo checkout's root with `run_in_background: true` run `drive job launch <j> - <<'BRIEF'`, the brief, and `BRIEF` (a job added without `--remote` that no local agent holds launches the same way; `drive job launch` refuses if run outside the checkout root or already started). Always pass a brief, handoff or message on stdin, including to `drive job resume <j> -`, rather than writing a file, because Claude Code reloads files written by the session after every compaction.
2. `drive job launch` starts an Orca worker on a Sprite through the `orca` skill's launcher on a dedicated Orca Run that only `drive watch` reads. Because Orca types notifications into the terminal bound to a Run, the coordinator's terminal binds a lane's Run only during start or reply and otherwise holds the drive's own Run; ignore any notification typed during those seconds and do not run `orca orchestration check`, since the watch turns lane mail into `JOB` events.
3. If worker start fails, have a reader check whether the attempt left the lane live before starting it again; if no worker started, run the job locally with the Agent tool on its brief and note that in the order's next report.
4. `drive watch` turns each Orca report into a `JOB <j> <o> <line>` event starting with `DONE`, `READY`, `BUILT`, `WAITING`, `ASK` or `BLOCKED` from the report's first line, setting the job's state just as a local return does. `drive status --json` holds the full latest report, and `drive job replies <j>` prints all results and questions oldest first with timestamps.
5. Because a Sprite holds no Buildkite or AWS credentials and no cci or cc-notes records, a lane requests reads with a blocking question starting `LOG <url>` (or `READ: LOG <url>`, ignoring trailing text) for Buildkite or GitHub Actions logs, or `READ <command>` for allowed `cci` or `ccn` commands. The watch runs `tools/ci bk`, `ccx vcs job-log`, `cci` or `ccn` in the drive's starting directory and replies with up to 12,000 characters, queuing the question across retries or watch restarts (`WATCH the answer to <j>'s read failed` needs no action). A disallowed or failing command produces `JOB <j> <o> READ unanswered`, and any other question such as `READ: please send <file>` arrives as a `JOB` event for you to answer.
6. Each minute the watch registers PRs from `READY` or `PR:` lines as wanting his tap, checks GitHub for untracked open PRs on the job's or lane's branch, and polls the lane's Dispatch: a dead worker emits `LANE … died`, and a `running` job whose lane sat at its prompt for 30 minutes, finished, or ended without resume for 30 minutes—or has an untracked open PR—marks its parts `ORPHAN`s.
7. Run `drive job resume` in the background because relaunching takes minutes (`drive job resume` refuses a local or unstarted job or an unreachable Sprite with exit code 2, and you resume again once the watch reads the lane). It sends the message to a live worker, starts a new worker in the terminal of a finished worker on a live Sprite, or relaunches a dead Sprite on the same Run with a handoff carrying the brief, branch, last line, report, PRs and message (unpushed work on a dead Sprite is lost). An `EXEMPT:` line still gets `drive pr set <url> --exempt <class>`, and a `SERVES: port of #N` line gets the `READY` row's check against #N.

The brief is the job's whole context, local or remote:

```
Order (his words): <verbatim; for drive tooling, its order's own "Drive tooling: …" words>
Serves: <"port of #N", "drive tooling" for a fix to a tool the drive runs on, under its own order and never his feature order's, or "his order" when the Order line asks for this build; a job for anything else is never started>
Goal: <the deliverable, one sentence>
Done when: <the check that proves it, e.g. installed and the installed version contains the merge; every PR releasable alone, by reference/landing.md: a release cut at its merge commit is safe by itself, its targets in any order, with nothing run after it, so a change that needs a later step is split until each PR is safe alone>
Where: <repo, base branch, existing branch or PR to adopt>
Runs as: <only for a pass, migration, backfill, conversion or bulk repair over a team's data: the service account in that team's cluster it runs as, and how it starts with no person's role, such as a pipeline or an in-cluster schedule>
Handoff: <a PR event or a built branch freed only: the PR URLs or the built branch, its head, the event line verbatim, and the INSTALL: and PROVE: lines the first builder returned>
Decisions that bind: <every ruling of his on the whole area this touches, never only on the order's own words: his words verbatim with their time and what they imply here, from answer_search; never an id alone>
Native: <where he sees or uses the result, such as a Slack post or card, the dashboard, a CLI he runs or a product UI, and what that platform already does for it, with links, such as Block Kit's chart and table blocks; "none" for work he never sees>
Would he ask: <what he would still have to ask for if only his words were built, such as the next piece, a link, or a native piece passed over>
Plan: <the plan section this implements, quoted>
Incident: <an incident job only: the record's id, which its owner, the first check or the cause job, keeps and every other job appends what it observed to; roll back to the newest build provably without the failing change, however many releases back; never a revert, which lands only on his tap; the fix starts at the alert's code path or the failed release's step and is the root fix of the cause, never a pin, flag, header, prefix rule, cap, retry, timeout raise, timer, wait, cache or special case; a card of his that blocks it never stops it: build the recommended option meanwhile; from the merged fix to its build nothing stops, no dry run, no cover or cause read, no comparison of open builds, no question; the job that merges the fix lifts the service's freeze, named here by its id, with tools/ci release unfreeze <id>; start the build at the fix commit with the cut reference/incidents.md names and report its link; the approve gate is the only check and reads run while it builds; return the inputs to a write-up, not the write-up>
Scratch: <the job's scratch folder>
Transcripts: <the transcript path of every earlier job on this order, so it reads instead of being told>
Drive: <name>, order <o>, job <j>
```

A job reports to another agent rather than to him: it pipes its full output on stdin to `drive job report <j> -` (the file-tools hook denies writing report files) and returns only the first line (`DONE`, `READY`, `BUILT`, `WAITING`, `ASK`, `BLOCKED`, or `DESIGN`), followed by one fact per line—links, numbers, paths, exact quotes, and unproven items— as inputs for the handler that writes prose. Whoever acts on the job reads it with `drive job report <j>`, while `ASK` blocks go through `drive job ask`.

- **His words, never a stand-in, and never the whole spec.** Carry his exact words and timestamps in `Order`, `Decisions that bind`, and cc-notes answers rather than paraphrases, card labels, or bare answer IDs, because an answer's title is the question and only its body holds his ruling. When he will see or use the result, fill `Native`, `Decisions that bind`, and `Would he ask` so the job uses the platform's built-in capabilities (such as native Slack Block Kit chart blocks rather than rendered images), follows his prior rulings across the area, and completes obvious follow-ups before returning.
- **His approval of a release approves it, right then.** His order or card pick to ship or approve a release (or an incident order's cut and rollback under [reference/incidents.md](incidents.md)) authorizes both the release and its approve gate, including migrations, deletes, and replaces: pass `--order <his answer id>` to `tools/ci release start` or run `tools/ci release approve <id> --via <agent>` at the gate without asking again, and carry that order across resumes or re-plans. Never approve a release or gate without his approval for that release, and never touch a release he started himself.
- **Answers resume; PR events start fresh.** Send his answer to an `ASK` back to the waiting job via `SendMessage` locally or `drive job resume <j> -` on stdin remotely. For any PR event after a builder returns—including a `BUILT` job's `FREE` event—start a fresh builder so it does not re-read the prior build context (builders compact at 300,000 tokens locally and remotely): run `drive job add builder`, claim each PR with `drive pr add <url> --job <new>`, pass the `Handoff:` line, prior `Transcripts:`, and verbatim card answers in `Decisions that bind`, and mark the old job with `drive job set <old> --state stopped --said "handed to <new>"`. Exception: always resume an incident job on every event to minimize user impact ([reference/incidents.md](incidents.md)).
- **A reproduction leaves one file.** A bug-reproduction job saves a single runnable file with ordered steps, exact prompt and code, build/version info, and measurements, and records it with `drive job set <j> --repro <file>` so `drive status` lists it for immediate reuse.
- **One deliverable per job, and no job waits on another.** When B needs A merged, start B on A's `DONE`.
- **A sweep over many units is one job running a Workflow**, started by you because a background agent cannot spawn agents.
- **A job's state is its transcript.** Before reporting on a running job, read its transcript with `cc-transcript` locally or `orca orchestration worker-read --dispatch <its dispatch> --limit 50 --full --json` remotely; silence is not evidence.
- **A stack is at most four PRs.** Keep stacks to four PRs or fewer by splitting into independent stacks or folding PRs together; the PR card check in `drive pr set --tap` and every card draw refuses a stack of more than four PRs.
